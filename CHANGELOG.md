# Changelog

All notable changes to Fledge are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/) and the project uses semver.

## [Unreleased]

## [0.4.2] — 2026-11-18

### Added

- Operators can set each data-retention window with a `RETENTION_*_DAYS` environment variable and preview a change before making it: the new read-only `node scripts/retention.mjs --dry-run --days N` prints, per table, how many rows that window would delete without deleting anything, and the `/admin` page gains a **Data retention** card with the effective window per class and its current count. A window below one day is refused by the delete path as well as by the config, so a direct `pruneOldData({ jobs: 0 })` throws instead of deleting every finished job.
- Fledge now reports the shared model router it depends on. With `MODEL_ROUTER_URL` set, `/readyz` gains a `router` object carrying the router's state and the latency of the health read, the metrics endpoint gains `fledge_router_*` series for key spend and budget, the rate and budget cooldowns and the queue depth, and an all-capped or unreachable router raises one operational alert to the superadmin through the existing cooldown and `ops.alert` webhook. A single cooling key is reported as `rate-limited` without failing readiness; only an unreachable router, or one whose every key is capped, makes `/readyz` answer 503. A deployment that sets no `MODEL_ROUTER_URL` keeps exactly the readiness body and the metrics it had before.
- Unattended runs can execute as a project service principal instead of the person who created them: the principal resolves to a project-bounded actor from its explicit grant, and a run records the principal and the revision it was created at, so a disabled, revoked or rotated principal stops the next run instead of borrowing a human's authority.
- A superadmin can now create the next mechanical release pull request from the Admin page. The action shows the current main commit, the latest release tag, the commits/fixes/features/fragments since that tag, the computed next version, the `ci-ok` result and the reason it is blocked, then dispatches the existing `daily-release` workflow after a typed confirmation and a recent GitHub re-authentication. It creates no tag, merge or deploy by itself; the normal release PR, gates, auto-merge, tag and publish chain still run. The dispatch token is server-side, repo-scoped and never rendered or logged.

### Changed

- The normal-user pages — dashboard, console, repository page and settings — now say workspace instead of FlyBot instance, and the start, stop and reinitialize controls are named for the workspace and each carry a one-line hint. The footer brand line and the stage-mode form values are unchanged.
- The schedule console now reports what actually happened to a run's notifications instead of the fixed `unknown`. A notification a job queued carries that job's id, so the console reads the outbox for the newest decided instant and names the state: sent, queued, sending, retry scheduled, failed or blocked. A finished run that queued no external notification reads `none`, a send that may have crossed the boundary reads `unconfirmed` and is never resent automatically, and a run whose job is still running reads `unknown` — a job queues its notifications only when it ends, so a missing value is never printed as a definite none.
- A scheduled run now continues an open work item only when its artifact is still live: before the scheduler chooses a follow-up (or a review), it reads the item's pull request or issue once, and a merged pull request or closed issue turns that choice into a fresh iterate on the repository's own goal instead — the stale row is marked with the state that was observed, so the next tick does not choose it again. An open artifact, a failed read and an item that names no link all keep the previous behaviour, and a held-back repository costs no read.
- A carried-over line that names no issue or pull request is now labelled `unverified (no link)` in the run's carry-over block and counted separately from lines whose artifact was checked, so the job page shows how many carried items rest on no link at all. The continuation instruction now offers only a line whose artifact was observed live: an unlinked line stays as context but is no longer presented as work to continue.
- The job page lists every carry-over item it dropped — each with its link and whether it is a closed issue or a merged pull request — and every line it could not verify, naming the failed read or the spent read budget, instead of only the counts in the header. A job whose goal happens to contain a carry-over line no longer prints counts nobody computed.
- The job page names the revision an adversarial review covered, beside the packet hash, and says so when an older record carries no revision instead of printing a hash that belongs to none. The repository review trend names its first-decision latency (one sample per work item, at its first review) instead of counting every review, and adds an override rate with its own denominator: merges that went past a recorded changes-requested decision, each naming the review job, the model and the tip it overturned. A review callback's reviewer words now reach the follow-up goal and the job page, bounded to one line; a review with no body produces exactly the goal it produced before.
- A successful work job no longer makes the repository wait out the 15-minute work-session cooldown: the next ready item is dispatched on the next scheduler tick, so a role that finishes is followed by the next item instead of a pause. The wait after a run that did not succeed and the doubling backoff after two unproductive runs are unchanged.
- The daily release drive no longer carries a `tag` action. The release job never supplied it the merged pull request list, so the action could neither run nor be reported while `docs/deploy.md` said it was; the tag job remains the only tag writer and repairs a merged release pull request without a tag on its push and scheduled runs.
- The Fledge documentation now lives at <https://docs.fledge.hugoxk.online/>. The app footer and email templates, the README files and the landing pages point there, and the old `fledge-docs.hugoxk.online` host redirects to the new one.

### Fixed

- The `main-health` reporter on the default branch no longer fails silently: when it cannot finish its report — a malformed `gh` answer, a refused write — it opens one label-less issue titled `ci: main-health failed to report` naming the commit, the run and the original error before the job fails, because a crashed reporter used to leave the same silence the red-`main` tracker was built to end. A crash on any other branch still writes nothing.
- A cancelled final CI run no longer counts as "CI reached the tip". The CI watchdog now dispatches one repair for a head whose `CI` runs were all cancelled, and prints the pull request as stalled when that repair is cancelled too, instead of leaving it with no `ci-ok` and no repair.
- A verdict comment written as `## REVIEW — PASS` now starts the `review-gate` job like any other case. The comment job's prefilter used to hold its own word list, which disagreed with the parser; it now asks the parser directly, after checking out the default branch, so the shapes that start the gate and the shapes the gate accepts cannot drift apart again.


## [0.4.1] — 2026-11-17

### Added

- Written-by: HugoXK

A repository can be shared with its members: the dashboard, repository page,
work items and jobs are visible to every active `repo_members` row, a `viewer`
reads without writing, a `developer` works without changing the merge policy,
and only a `maintainer` writes repository settings, changes the role, deletes
the repository, publishes a release or stops and restarts its workspace.
- A job now records one `job_attempts` row per dispatch, naming the worker, the attempt number and the lease epoch it owns; the running transition and the attempt commit together, and the stale-running/lease sweeps close a dead worker's attempt as `reaped` instead of leaving a silent reset to queued. A report that arrives from a lease epoch that was taken over is refused and recorded on the attempt it lost, so a late success cannot rewrite a reaped run.
- An iterate job's goal now carries one line of temporal context — `Since 4f2c1a9: 3 commits ahead, 2 merged PRs (#812, #815)` — built from the previous finished run's base SHA, and the job page shows the same line. A first run says `Since: no previous run`, and a compare that failed or a page walk that hit its cap is marked `partial` instead of reporting a smaller number.
- An issue body that tells the agent to push to main is now recorded as named, blocked directives on the job page instead of only being fenced as data. The firewall matches a finite rule table and stores rule ids plus the body hash, never the text.
- A job can now stop and ask instead of guessing: a terminal callback may carry one bounded `decision`, the job waits as `paused`, the question appears in the existing inbox marked with its job, and the first answer starts exactly one retry whose goal carries the question and the answer.
- Each repository now has a development strategy that is versioned and content-addressed: a strategy page shows the bundle version and hash it is on with each section's source, and a maintainer can freeze the current strategy as a new candidate. A stale page is refused with both versions, and a strategy that names a frozen section — evaluator, evidence, CI, merge gate, auth, gateway or capability — is refused before anything is written; stable is never moved by freezing.
- Every job now records the development strategy it was created under — its content hash, its version when that content was frozen, and the section map itself — and the job page shows it. When the repository's strategy changed since the previous job, the page names the section keys that moved, and the earlier job keeps its own hash so history is read rather than rewritten; a job created before this change says it has no recorded strategy instead of showing an empty one.
- Notifications now go through a durable outbox instead of a best-effort call: job, digest and question mail and the operator webhook are queued with an idempotency key, retried on a definite transient refusal, marked unknown when a request may have reached the destination (never resent automatically), and shown with their delivery state in the admin console, where an explicit resend reuses the same key and is audited.
- A schedule's console now has a **Run now** button: one explicit run from the current
moment, identified by the key the page rendered, so a double click starts one run
and a new page starts a new one. It never moves the schedule's next run.
- A schedule on a repository can now be paused and resumed from its console. While it is paused the worker records each instant that passes as skipped with reason paused instead of running it, so the window is visible afterwards and resuming starts from the next instant rather than replaying a backlog. Pausing and resuming are maintainer actions and are audited.
- Written-by: HugoXK

A failed release run can now be explained from the repository page. An explicit
maintainer action reads the failed job logs of the run the release recorded
through a read-only GitHub App token that is revoked when the read ends, redacts
the text before it is cut, and shows a bounded excerpt with the exact log lines
it kept and a link to the job page. The analysis never changes the release state,
creates a Release or reruns a workflow, and a repository without an installation
is refused instead of being read with a wider user token.
- A draft Release prepared for a connected repository now carries notes built from the release range — the merged pull requests and commits between the previous tag and the confirmed target — with each source listed once and linked, instead of a placeholder sentence. The repository page lists the exact sources the draft was built from.
- A review that requests changes now starts a fix through a budget instead of without one: a third-party review bot can cause at most one fix per pull request, and the platform's own reviewer at most three per head (a repository can lower its own ceiling with the `repo:<id>:max_revisions` setting). A person's requests are never counted, a repeated request is still answered by the existing duplicate-fingerprint guard before any budget is spent, and every refusal writes one `trigger.revision_refused` audit row. The count resets when the pull request head moves, and a request that arrives while a review is already running keeps its author into the replay, so the fix it starts is counted exactly like one that started immediately.
- The admin metrics page gains an `Automation health` card and `/metrics` gains the series behind it: how long a repository has had ready work with no active job, the dispatch latency from ready work to a started job, and the queue depth. A repository whose ready work waits longer than `AUTOMATION_IDLE_ALERT_MINUTES` (default 30) now raises an `automation_idle_with_work` alert that clears when a job starts, and `FledgeDispatchLatencyHigh` pages when the p95 dispatch latency is above 15 minutes.
- A provider model its provider has stopped serving is recorded as retired with the date: Settings and the repository page say so, the job's model line names the reason, and an apply that would restart a workspace onto that model is refused with its name.

### Changed

- The job page now opens with one review → merge card: a single sentence and a single action for the current state, with the head SHA, the verdict that covers it, checks, path and evidence, base movement and queue state in the same card. A verdict recorded at an older tip, a moved base and a blocked check each have a named state, and the card refuses to offer the merge control for them. The per-pull-request merge control lives on that card; the repository page links to it and keeps its bulk "merge all clean PRs" action.
- A refused repository setting is now visible where the mistake is: the repository Settings form marks the invalid interval with `aria-invalid`, describes it with an `aria-describedby` message under the field, and moves focus to it, while the page banner keeps only a short summary instead of repeating the sentence. A submitted interval the form never offered is refused rather than silently clamped, and a legacy row whose stored interval is not in the offered list can still be saved unchanged.
- Every line the carry-over block states about earlier work now says when that state was observed and what it was — `observed 07:12Z open` — from the same read the block already spent, and the job page shows the same observation after the run instead of re-deriving it. A read that failed says `observed unverified` and carries no time, a pull request closed without merging is `closed` rather than `open`, and a job from before this change says the observation was not recorded instead of showing a borrowed time.
- The repository header now names the interval it prints as the discovery cadence — "Discovery every" / 发现间隔, the word the Add-repository and settings forms use — and reports it at the one-hour floor discovery actually applies, instead of reading "Auto every" beside the automatic-work switch. Automatic work stays an on/off switch, and a repository with a saved schedule still shows the schedule's next run as the answer for when a run happens.
- The `ci-ok` check that gates a merge is now also published by a `workflow_run` workflow, which GitHub always takes from the default branch, so a pull request can no longer rewrite the aggregate that judges it without losing the merge. The aggregate job inside `ci.yml` keeps publishing `ci-ok` for one step so the change itself can merge; branch protection still requires `ci-ok`.
- The console now uses the warm editorial palette: charcoal and warm paper surfaces, a copper interactive accent, sage and sand brand hues, a serif display face on the page title, wordmark and hero heading over the system-sans body copy at 14px/1.55, a 6/8/10/12 radius scale and one tight shadow kept to menus and dialogs instead of an 80px glow on every card. The letter-spaced uppercase section labels are gone, and both palettes keep their WCAG AA contrast ratios.
- A release now closes its own chain: the publish job scans and smoke-tests the exact digest it pushes, runs the verification it used to leave to an operator, attaches the SBOM to the GitHub Release instead of an expiring Actions artifact, and refuses to repoint the `vX.Y.Z` image tag at a different digest.
- Feedback is now a global dialog opened from the footer, so sending a note no longer leaves the page. The Settings form remains as the no-JavaScript fallback and keeps the feedback history, the duplicate feedback button in the About card is gone, and submitting returns to the page the note was written on.
- The work board and the scheduled work selection now share one FIFO order: at equal priority the oldest work item is first. A recently edited item can no longer jump ahead of an older one that has been waiting, so the backlog is drained in the order it arrived.
- The GitHub star link in the footer and the Settings About card now uses a drawn line-star icon with a compact label instead of the `★` text glyph. The URL, the About copy and the accessible name are unchanged.
- The console moves to a flight-deck visual system: a cool mineral and pine palette with brass as the only warm note, flat section rules and square controls instead of identical rounded cards, a dashboard masthead with a Connect → Goal → Work → Review → Merge loop rail, sentence-case labels, and the About card removed from Settings.

### Fixed

- Written-by: HugoXK

The console merge button now runs through the management contract: a merge whose answer from GitHub is lost leaves an `unknown` receipt instead of a 500, and submitting the same form again reads the pull request back, records the merge once (work item, PR state, audit) and never merges it twice.
- The console's create, resume, retry and policy commands now resolve the actor from the database like cancel and pause, so every command on one repository shares one tenant-scoped idempotency receipt instead of a retried form writing a second receipt under an empty tenant; the identity backfill also stops rewriting its unchanged report row on every boot, so a read-only volume no longer fails to start over a write that changes nothing.
- `scripts/rotate-github-token.mjs` now proves a rotation instead of assuming one: inside a single run it checks the old value against `GET /user` and only deletes its timestamped backup when the old value answers `401` while the new one answers `200`. A still-live old token exits `2` and keeps the backup; an inconclusive pair exits `1`; and a new token whose `user.login` is not `EXPECTED_LOGIN` (default `HugoXK`) is refused before anything is written.
- The measured clock offset is now used, not only reported. Above the same 120 seconds the alert rule fires on, `/readyz` answers 503 with `clock.state: "fail"`, `Jobs.enqueue` refuses with `CLOCK_SKEW` before any job row is written (counted as `fledge_admission_rejected_total{reason="clock_skew"}`), and the App JWT refuses with `CLOCK_SKEW_EXCEEDED` instead of signing from a stale correction. A reading is trusted for fifteen minutes, after which the clock is `unknown` and signing fails with `CLOCK_SKEW_UNVERIFIED`, so a GitHub outage can no longer keep a wrong correction alive. Stored timestamps are unchanged and a wrong host clock still needs the host fix.
- Deleting a model provider, or one of its models, no longer silently moves the repositories that used it onto the platform default model. The affected workspaces are marked as needing a model restart and the console names how many repositories were affected, so the change in spend is a visible decision instead of a silent one.
- The daily release waits for the `ci-ok` verdict instead of reading it once: a run whose aggregate is still in progress is re-read at the same tip up to three times, five minutes apart, so a green tip that was still running no longer loses the slot, while a red aggregate still blocks at once. The release summary names the `ci-ok` run id, its status and how many reads were made.
- A release that was left half-made is now finished by the routine instead of by a human: when the tag exists but its GitHub Release does not, the tag job dispatches the publish run instead of skipping, and the scheduled slot repairs a merged release pull request whose tag is still missing. A tag that already has its release stays a no-op, a publish run that finds that release in place stops before it builds an image, and only the squash of the merged release pull request can trigger either write.
- A webhook send that may have reached the destination is now classified `unknown` even when Undici puts the socket code on `error.cause`, so it is not resent automatically; a transient resolver failure is retried instead of being marked `blocked` permanently.
- The current setup step's mark now paints its ink in `--mark-ink` on the `--accent` fill instead of `--accent-ink`: at 12px the old pair was 1.92:1 in the dark palette and the new one is 9.30:1. The AA guard in `test/uiTokens.test.ts` now covers every token ink painted on a token fill in both palettes, so a rule cannot reintroduce an unreadable pair without failing the build.
- The automation alert no longer reports a repository the dispatcher refuses for an exhausted platform quota as idle with work. The refusal and the alert now read one predicate, so quota joins approval and instance readiness as a reason the scheduler names; a user with their own model, or a repository with its own model selection, is unaffected because the platform pays nothing for it.
- A deploy now copies every file of the release it is deploying, including one whose new content happens to have the same byte count and the same timestamp as the file it replaces. Before this, rsync's size-and-time check could leave that single file from the previous release in place while the rest of the tree was replaced, so the host could serve one old file beside a freshly built version: a file under `public/` was refused by the rollout gate's whole-tree comparison and rolled back, but a file outside it, such as `package.json` or a source file, was served unseen because the gate compares only `public/`.

### Security

- A per-repository FlyBot container now starts with a read-only root, a single writable tmpfs at `/tmp`, every Linux capability dropped, `no-new-privileges`, a non-root user and the existing CPU, memory and PID ceilings, and the host Docker socket is never mounted into it. A new isolation check starts a throwaway container with exactly those arguments and asserts each fact from inside it — the root refuses a write, the effective capability set is empty, a seccomp filter is loaded, the socket is absent, only the repository's own data directory is a host bind, and a container on another tenant's network is unreachable — and exits 3 where no Docker daemon exists instead of reporting a pass. The builder also refuses a data directory that is not an absolute existing directory, so the one host path a tenant container sees cannot be a relative path the daemon resolves elsewhere or a path Docker would create as root. Egress is unchanged in this slice.
- A `TRUST_PROXY` whose entries together cover the whole IPv4 or IPv6 space is now refused at startup, the same way a `/0` range already was: host bits are masked, the entries are combined, and an IPv4-mapped prefix such as `::ffff:0:0/96` counts as the IPv4 range it actually trusts. An installation running such a list will not boot until the env names the proxy address or its narrow CIDR; a list that stops short of the whole space still starts. Separately, a request address that cannot be parsed - for example nine groups forwarded verbatim by a trusted hop - now falls into one shared rate-limit bucket instead of answering 500.
- Issue text sent to the agent from `/fledge plan` and `/fledge fix` is now wrapped in a labelled untrusted block. A forged fence is escaped, control characters are stripped, the 4,000-character cap is kept, and the job audit records the label and a hash instead of the body.
- Account identifiers no longer reach the log sink, and a development outbox file no longer carries the recipient in its name. A log line masks an email, a GitHub login, a user id, a token and an IP address in every string field — including fields the sink does not name and values nested inside an object or an array — while the stored job row and the job page keep the real value an operator needs; `npm run mail:outbox` expires every `.eml` older than `MAIL_OUTBOX_RETENTION_DAYS` (7 days by default) and then prints the newest one.
- Deleting an account now also removes its captured error reports and its feedback triage rows, and the delete preview counts them. Both tables point at the account with a foreign key that clears the id instead of deleting the row, so the login, the page path, the error text and the triage message survived the deletion and stayed readable; the purge now deletes them explicitly before the account row.
- The release publish job no longer leaves the workflow token in `.git/config` while it installs dependencies from the tag, so a dependency lifecycle script cannot read a token that carries `contents: write`, `packages: write`, `id-token: write` and `attestations: write`.
- The review gate and the PR lint no longer judge a large pull request from a capped prefix of its file and commit lists. Both read until the API returns a short page and refuse, by name, a list that does not match the file and commit counts the pull request reports, so a T3 path or a reviewer-authored commit past the old cap can neither pass without a PASS nor be searched for.
- A T1 change is no longer merged unreviewed when its diff weakens the test suite or adds client-side script: deleting an `assert.`/`expect(` line under `test/`, adding an always-true assertion, or adding an inline `<script>` under `public/` now raises the computed tier to T2, which needs a PASS at the tip. Client-side `.js`/`.mjs` under `public/` are T2 by path, and the CI risk job, `review-gate` and `pr-lint` all classify through one function, so a `risk:T1` label and the PASS the gate demands cannot disagree.
- Publishing a release, from the release form or from the readiness page's tag button, now needs a fresh GitHub confirmation and is paced by the destructive class limit like the other privileged writes, and its preflight refuses a target commit the default branch does not contain instead of tagging it. The containment check reads `compare/{defaultBranch}...{target}`, where `behind` and `identical` mean the default branch contains the target; a target that is `ahead` of the default branch or `diverged` from it is `target_not_on_default`, and a compare that cannot be read is refused rather than assumed. A tag push runs the workflows committed in the tagged tree, so the ancestry check is what keeps "this release was built from this repository at this commit" checkable. The previous-version scan walks the tags newest-first and stops at the first one reachable from the target, so a release cut from a commit older than the newest tags still sees its real previous version instead of skipping the "nothing to release" and "not higher" refusals.
- A release publish run no longer reads a failed lookup as "no release yet". The publish job and the tag job now classify the GitHub Release lookup in one place (`scripts/lib/release-lookup.mjs`): a successful read is present, a 404 is absent, and every other failure — a 403 from a narrowed token, a 5xx, a dead network — is unreadable, so the publish run exits non-zero before it builds, pushes or attests anything and the tag job exits before it plans a tag. Previously a 403 was recorded as "not published" and every write step ran, so a transient read failure could republish a tag's image and rewrite its notes. The publish job's final step also refuses to edit a release it did not create: a release that appears during a run is an error, not a notes rewrite.


## [0.4.0] — 2026-11-16

### Added

- A scheduled job's carry-over block now checks the issue or pull request behind each line before it is carried: a closed issue or a merged pull request is dropped instead of sending the next run after finished work, the block states `carry-over: N used, M dropped (closed/merged)`, and the job page shows that line. A read that fails keeps its line and counts it unverified rather than dropping it silently.
- The job page now opens with a "Why this change" block: what the agent said it changed, the risks it named, what it ran, and the size of the diff, read from the pull request body and its changed-file totals. A section the body does not carry says "not stated" instead of guessing, a repeated heading shows the last one and says so, and a pull request that cannot be read leaves the page at 200 with the unavailable fact named.
- A personal `flg_` token can now read your own jobs. `/settings` offers two scopes when minting a token: `gateway` for the model endpoints, and `jobs:read` for the new `GET /api/v1/jobs`, which answers your jobs newest first, paged by a cursor instead of an offset. The token's scope is the whole capability, a token outside it is refused with `403 insufficient_scope` rather than downgraded, and a missing, revoked or expired token is `401 invalid_api_key`. Both surfaces now share one authenticator, so what a token is and how it is refused cannot drift apart.
- `npm run evolution:export` now writes one dataset with a stable identity instead of a bare row array: a `ds_` id, the source window, the repositories, the row count, a sha256 `contentHash` over the canonical manifest and rows, a train/holdout split that keeps every repository on one side, and the holdout entries a promotion must not repeat. Every exported string is passed through the platform redactor, and only repositories an admin opted in with `npm run evolution:consent -- --repo owner/name --on` appear at all; consent is off by default and every change is audited. `--report` prints the manifest's own split counts, and the exporter still opens the database read-only and never writes to it.
- Repositories can now declare Fledge rules and text skills under `.fledge/` and `.agents/skills/`. Fledge reads them from the default branch at a fixed commit, records every file hash on the job, includes the rule text in the prompt, and serves a skill's full text on demand through a job-scoped context endpoint. A maintainer can also set a console override for each of the three rule files; the repository file still wins, the override applies only when that file is absent, and the job records which layer was effective. A pull request that changes a rule or skill file is flagged and blocks auto-merge until a maintainer acknowledges that head SHA. The set is bounded (32 KiB per rule or skill file, 32 skills, 256 KiB in total, and 16000 bytes of assembled rule text in the prompt) and an oversized set is refused as a whole instead of being truncated; the refusal names the file that crossed the limit.
- The repository page now opens a read-only CI gate check. It answers three questions from evidence it reads on GitHub: whether a workflow triggers on `pull_request`, whether that workflow runs a test command, and whether the default branch requires that check before merge — plus whether a pull request merged in the last two weeks landed without a successful check. Every gap names the workflow file or the branch it read. The check creates no branch, commit or pull request; proposing and opening the gate pull request is a later slice of #543.
- A confirmed repository gate plan can now be applied: Fledge creates one pull request that installs the four-lane gate contract, the gate script and the tag-triggered release workflow. An existing workflow keeps its unrelated jobs and triggers and gains only the pr-ready gate job; a plan whose base branch moved after analysis is refused before anything is written, and a session can create its pull request only once.
- A repository page now answers whether it can be released before a version is typed. The read-only release-readiness view names the latest SemVer tag, the commits and merged pull requests since it with how many are features, and whether a `changelog.d` fragment is pending — or prints, in the same words the tag form refuses with, why a release would not go ahead. It creates no tag and no Release, and needs no release-scoped token.
- The release-readiness page can now create the release tag itself: a maintainer confirms the version on the page, and the tag is written on the commit the page showed. The default branch is read again immediately before the write, so a page left open while `main` moved is refused with both commits named instead of tagging a tree nobody looked at — a tag is never moved or deleted, so a stale target costs a version rather than a retry. A refused write that is really a missing permission says the installation needs `Contents: write`. The action creates the tag and nothing else: no Release object and no draft notes.
- A comment that mentions the bot (`@fledge` by default; `FLEDGE_MENTION_NAMES` changes the names) now starts work: a mention on a pull request starts a review of that pull request at its head, and a mention on an issue starts a follow-up for the issue that may open one branch and one pull request. A second mention at the same head does not create a second job, a newer mention replaces a queued job that has not started, and a running job is never interrupted — it finishes first. The trigger uses the same trusted-author filter and per-comment dedupe as the `/fledge` commands, and records the comment, the head SHA, the actor and the outcome.
- Jobs now show a closed P0–P3 priority ladder instead of a bare integer: P0 ongoing damage, credential exposure or an outage; P1 the core goal is blocked; P2 ordinary work (the default); P3 non-core polish. Raising a job to P0 or P1 is a claim, so it needs a reason and evidence a second person can check — a link, a commit or ticket sha, or a measurement with a unit; adjectives are refused. A real priority change moves the job to the tail of its new level, saving the level it already holds keeps its queue ticket, and a running job is never interrupted by a later P0. Tasks can also be linked explicitly now — same problem, related or recurrence — with a reason and checkable evidence, but only inside one repository: a similar title never merges two tasks, and a relation never moves or suppresses work. After a job is verified, the follow-up is one bounded decision — a new task, a supplement to an existing one, or a related/recurrence task — with a reason and checkable evidence; a contradictory `new` aimed at an existing task is repaired once, and when the decision is unavailable the default is a separate task at P2. A related task never takes the claim of work already running: it leaves one notice the running job reads at its next checkpoint.
- A pull request that changes only `deploy/` now gets a `deploy-check` job instead of a review-only pass: the Cloudflare email worker is parsed with `node --check`, the Prometheus rules are validated with a checksum-pinned `promtool`, and the nginx/systemd samples are checked where the runner provides those tools (a missing tool is recorded in the job summary as a gap). The change classifier gains a `deploy` flag, and a diff that mixes `deploy/` with `src/` still runs the code gates, so a deploy file cannot buy a source skip.
- The restore checks now also restore a small fixture written by the previous release and migrated by the current build — `npm run db:prev-release:restore`, and the same check inside the test suite — so a column renamed or dropped without a migration fails on a fixture instead of on a real upgrade. A wrong or lost key reports `key-mismatch` and never passes, and `docs/deploy.md` records the fixture's provenance and the regeneration command.
- Repository and user budgets now sit beside the per-job budget: a maintainer can cap a repository's rolling 30-day spend or one person's spend across repositories, each with alert, pause or cancel. Every scope reads the same single checkpoint, the refusal names the cap that fired, precedence runs job → repository → user, and the repository page shows each scope's cap, its spend and a lower-bound caveat when a call could not be priced. The same report and `docs/observability.md` now state what the success rate is a rate of: only `succeeded` and `failed` jobs are counted, so `cancelled`, `paused` and `quota_exhausted` are excluded from the numerator and the denominator alike, and the alert rule's numerator and denominator are pinned to those same exported statuses so the two cannot drift.
- On a tablet the sticky header is now one fixed 64px row instead of a two-row block that stood 215px tall between 641px and 960px, and the main navigation opens from the same labelled toggle the phone already uses, so a 768px screen keeps its content under a header that reserves 90px even without JavaScript, in both Chinese and English.
- The daily release now follows the weekly cadence: the first release of an ISO week bumps the minor, and every later release in the same week bumps the patch. The planner reads the last tag's commit time and the workflow's run time, and the review gate uses the same rule so a patch release PR still earns the mechanical-release exemption.
- Switching a repository to a new model provider now updates every role bot before Fledge reports success. If any bot is skipped or the update fails, `models_dirty` stays set, the failure is audited and the API returns `BOT_MODEL_ASSIGNMENT_FAILED` instead of a false success. Bot models are also reconciled after provisioning and immediately before job dispatch; a job is not sent to a team whose bots still point at the wrong provider.
- Fledge now removes a persisted `/data/bot/state.lock` before provisioning or restarting a FlyBot container. A container restart can reuse the same namespace PID, so a stale lock made the new DSH treat its own team as owned by another window and become read-only; removing the lock lets the restarted DSH create a fresh one. The health-driven auto-restart and model-apply restart both use the same path.
- Instance health checks now ask the bridge for DSH `state`, not only `/healthz`. A container whose `dsh web` process has exited is marked failed instead of ready; when no job is active and restart is safe, Fledge restarts the container, waits for DSH and records an audit entry, with a ten-minute cooldown. An instance with an active job is never restarted by the sweep.
- The instance health sweep now probes failed instances as well as ready ones. If their bridge and DSH answer again, Fledge moves them back to ready, clears the last error and records `flybot.instance.recovered` instead of leaving the repository offline until a manual restart. Stopped and provisioning instances are still skipped.
- Scheduled iterate jobs are no longer skipped just because a repository has an open work item. The scheduler still enforces one active job per repository and the duplicate-issue preflight still runs, but `pr_ready`, `in_review` and stale `in_progress` work items no longer stop auto-iteration. A failed job now returns its `assigned`/`in_progress` work item to `triaged` instead of leaving it active forever.
- Fledge now reconciles stored team session IDs with the live DSH state after a health probe and immediately before dispatch. A DSH restart that creates new Chief/Lead/Product/Test/Security/Reviewer/Dev sessions updates `team_json` and `chief_session` before the next job, so a job is never forwarded to a dead session and reaped as stalled. The refresh is audited and leaves the stored team untouched if any role is missing.

### Security

- `/metrics` now accepts its token only from `Authorization: Bearer <token>`, compared in constant time; the `?token=` form is refused, because a scrape URL ends up in proxy access logs, browser history and `Referer` headers. A production process refuses to start without `METRICS_TOKEN`, and refuses a `NOTIFY_WEBHOOK_URL` that is not an absolute `https:` URL, since that webhook carries the alert payload and its bearer secret. The loopback fallback for an empty token remains outside production only, and it is judged on the peer the trusted `TRUST_PROXY` hop saw, so a forged `X-Forwarded-For` cannot make a public request look local. Existing production deployments must set `METRICS_TOKEN` (for example `openssl rand -hex 32`) before upgrading; the direct-nginx install needs no `TRUST_PROXY` change.
- The rate-limit buckets behind token login, sign-in, the OAuth callback, approval and the job/webhook APIs now key on the client address the trusted proxy saw, so rotating a caller-supplied `X-Forwarded-For` no longer mints a fresh bucket, IPv6 clients are bucketed by their /64, and `/metrics` shares the API bucket instead of answering unauthenticated requests for free. The trusted hops are set by `TRUST_PROXY` (loopback by default, so the direct-nginx install needs no change); anything that is not an address or CIDR - `true`, `all`, a `/0` range - is refused at startup, because it would trust the caller-supplied end of the header.
- The build now proves more before a merge: gitleaks scans the commit range for secrets, actionlint plus a template-injection checker lint the workflows, the container image is scanned for high and critical vulnerabilities and then started to check `/healthz`, the whole dependency graph is audited alongside the runtime set, and a measured line-coverage floor fails the build if coverage drops. A required job that reports `skipped` now fails the aggregate instead of passing it. Release images are published with a build-provenance attestation and an SBOM, which `gh attestation verify` checks. The required check set, with the up-to-date rule, is recorded in `.github/agent/required-checks.md`.
